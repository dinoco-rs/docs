# Dinoco v2.2.3

Esta página acompanha o que mudou release a release. Cada item linka para a página que documenta a funcionalidade em profundidade — trate isto como um changelog, não como a referência principal.

## v2.2.3

- **Seeds rodam no runtime que o `#[tokio::main]` monta.** O `dinoco seed` rodava a seed num runtime Tokio de uma thread só, então código da aplicação chamado por ela que usa `tokio::task::block_in_place`, ou bloqueia esperando uma task que criou, entrava em panic ou travava. Agora ela roda no runtime multi-thread, como o runner de antes da v2.2.2 fazia. Veja [Como as seeds rodam](/pt-br/docs/orm/tooling/seeds#como-as-seeds-rodam).
- **O `dinoco seed` compila só o pacote em que roda.** Ele seleciona o pacote do diretório atual e só a library e os binários dele, então na raiz de um workspace com `default-members` ele não compila mais os outros membros, e um pacote sem library nem binário recebe um erro em vez de rodar os testes de integração e doctests dele.
- Atualizando: nada muda para o código existente.

- **Seeds enxergam o crate inteiro.** O `dinoco seed` compilava a seed num runner separado só com o `dinoco/mod.rs`, então `use crate::{...}` encontrava os models e mais nada: helpers, constantes e tudo o que a raiz do crate importa falhavam com `unresolved import`. Agora a seed roda dentro do crate da sua aplicação, por um teste que o `dinoco/mod.rs` gerado declara, então `crate::...` resolve exatamente como na aplicação, com as dependências dela. Veja [Como as seeds rodam](/pt-br/docs/orm/tooling/seeds#como-as-seeds-rodam).
- Atualizando: rode `dinoco models generate` uma vez para que o `dinoco/mod.rs` declare o teste da seed; até lá o `dinoco seed` pede isso. O crate é compilado com `cfg(test)` para rodar a seed, então ali o `connect()` gerado devolve o banco de teste: use o `client` que a seed recebe.

## v2.2.1

> [!WARNING]
> Mudança incompatível: todo field de navegação "um" agora é `Option<Box<T>>`. Regenere os models com `dinoco models generate` e siga os passos de atualização no fim desta seção. O schema, o SQL e o banco não mudam.

- **Models nunca guardam outros models por valor.** Um field many-to-one ou one-to-one era gerado como `Option<T>` (com `Box` só quando as relações formavam um ciclo), então um model guardava todo model para o qual apontava, esses guardavam os deles, e o espaço era ocupado com o include carregado ou não. Num schema de pagamentos em que uma mensagem de suporte aponta para o chamado e o autor, e esses para cobranças, empresas e contas, um `SupportMessage` ocupava 13.992 bytes, um handler que o mantinha através de um `.await` tinha um future de 22.592 bytes, uma transaction que o lia e fazia uma escrita, um de 42.680 bytes, e ler uma mensagem com includes aninhados mais essa transaction precisava de 1,1 MiB de stack num build debug. Todo field "um" agora é `Option<Box<T>>`, 8 bytes carregado ou não: a mesma mensagem ocupa 160 bytes, o handler 584, a transaction 544, e o fluxo roda em 116 KiB de stack. Os fields continuam sendo lidos através do `Box`, e o serde lê e escreve o mesmo JSON. Veja [Tipos dos fields de navegação](/pt-br/docs/orm/guide/relations#tipos-dos-fields-de-navegacao).
- **Futures menores em todo builder.** O `execute` guarda cada parte do builder uma vez em vez do builder e de uma cópia dele, leituras de um único statement devolvem o future da ida ao banco em vez de uma `async fn` em volta dele, o `find_and_update` aguarda atualizações de relação em `Box` como o `update` já fazia, e uma transaction guarda o resultado da closure uma vez enquanto faz o commit. Com o mesmo schema, `find_first` e `find_many` (com ou sem includes) foram de 1.112 para 392 bytes, agregações de 1.400 para 360, `find_and_update` de 824 para 176, `update` de 280 para 104, `count` de 408 para 248 e `exists` de 208 para 72.
- **`Float @default(0)` compila.** Um default de número inteiro num field `Float` gerava `#[dinoco(default = 0)]` num `f64`, que não compilava. Agora gera `0.0`.
- Atualizando:
  - Rode `dinoco models generate`. Nenhuma migration é necessária.
  - Ler os fields de um model relacionado compila como antes: `if let Some(account) = &session.account { account.email }`, `session.account.as_ref().map(|account| &account.email)`.
  - Código que precisa do model relacionado por valor o tira do `Box` com `*`: `let account: Account = *session.account.expect("account")`, ou `session.account.map(|account| *account)` para um `Option<Account>`. Um valor montado a partir de várias relações, como `Option<(Account, Business)>`, vira `Option<(Box<Account>, Box<Business>)>`, a menos que você tire cada um do `Box`. `session.account.as_deref()` dá um `Option<&Account>`.
  - Código que preenche um field "um" coloca o model num `Box`: `session.account = Some(Box::new(account))`.
  - Structs com `#[derive(Entity)]` escritas à mão continuam funcionando com `Option<T>` ou `Option<Box<T>>`.
  - No `dinoco/transform.rs`, `Relation::ty` é `Box<T>` para toda relação "um"; `relation.target` continua nomeando o model para o qual ela aponta.
  - Os métodos `execute` dos builders devolvem `impl Future` em vez de serem `async fn`, assim como os métodos de `dinoco_engine::Backend` que rodam um único statement (`query`, `aggregate`, `lookup`, `insert`, `update`, `delete`, `count`, `exists` e as leituras de relação), que agora compilam o SQL quando chamados em vez de no primeiro poll. `.execute(&client).await` não muda.

## v2.2.0

- **Ordene por várias colunas.** Cada chamada de `order_by(...)` agora adiciona uma coluna depois das anteriores em vez de substituir, então `.order_by(|x| x.created_at.desc()).order_by(|x| x.id.asc())` compila para `ORDER BY created_at DESC, id ASC`. Funciona em `find_many`, `find_first`, `pluck`, agregações sobre uma janela de rows e includes, onde também ordena a janela de `take`/`skip` de cada parent. Depois de `.group_by(...)`, um segundo `order_by` no field agrupado escolhe como empates na agregação são desfeitos. Veja [Ordene os resultados](/pt-br/docs/orm/orm/find-many#ordene-os-resultados).
- **Agrupe datas num fuso horário.** `.with_timezone(&zone)` depois de `date()`, `day()`, `week()`, `month()` ou `year()` de um field `DateTime` calcula o período nesse fuso em vez de UTC, horário de verão incluído: `.group_by(|order| order.created_at.date().with_timezone(&Sao_Paulo))`. Os fusos vêm do `chrono_tz`, agora reexportado como `dinoco::chrono_tz`. O PostgreSQL usa `AT TIME ZONE`, o SQLite uma função que o Dinoco registra em cada conexão, e o MySQL `CONVERT_TZ`, que precisa das tabelas de fuso horário dele: sem elas a query falha com uma dica em vez de agrupar sob `NULL`. Veja [Agrupe por data num fuso horário](/pt-br/docs/orm/orm/find-many#agrupe-por-data-num-fuso-horario).
- **Includes: filtros e páginas em todo nível, documentados.** Filtros de relação, `where_complex`, `order_by`, `take` e `skip` valem em todo nível de includes aninhados e em todo tipo de relação, e includes leem dentro de transactions pelo `tx`; testes novos cobrem tudo isso no SQLite, PostgreSQL e MySQL. A página de includes dizia, por engano, que leituras com includes não rodavam dentro de uma transaction. Veja [Ordene e pagine a relação](/pt-br/docs/orm/orm/includes#ordene-e-pagine-a-relacao).
- **Seeds.** O `dinoco/seed.rs` (ou `dinoco/seed/mod.rs`) guarda as rows que todo ambiente precisa, escritas com os models e builders gerados numa `async fn seed(client: &DinocoClient)`, e o `dinoco seed [--workspace nome]` roda ela no banco do workspace. O `dinoco/mod.rs` gerado a declara como `pub mod seed`, então o editor confere ela contra os models atuais. Veja [Seeds](/pt-br/docs/orm/tooling/seeds).
- **O runner reaproveita a sua build.** O programa que aplica o `dinoco/transform.rs` (e agora roda as seeds) compila no target directory do seu projeto com uma cópia do `Cargo.lock` dele, então não compila mais o Dinoco e os drivers de banco uma segunda vez: uma primeira execução que levava cerca de um minuto e 1,2 GB agora leva poucos segundos depois que a sua aplicação está compilada. Veja [Onde o transform roda](/pt-br/docs/orm/guide/transforms#onde-o-transform-roda).
- Atualizando: código que chamava `order_by` duas vezes esperando que a segunda substituísse a primeira agora ordena pelas duas; remova a primeira chamada. Quem monta queries à mão com o `dinoco_engine`: `FindQuery::order_by` é um `OrderByList` (`FindOrderBy::Asc("id").into()`), `AggregateGroup` tem um field `then_by` (`None` mantém a ordem antiga) e `GroupBy` tem uma variante `DateIn`.

## v2.1.9

- **Enums em colunas de string.** `#[derive(DinocoRuntimeEnum)]` transforma um enum Rust nos valores de uma coluna `String` comum, como permissões guardadas como `permission:view-users`: a coluna continua string no schema e no banco, sem tipo enum nem migration. Um field do model que guarda o enum lê variantes e grava strings em todo builder (inserts, `update`, `update_many`, `find_and_update`, filtros, filtros de relação, `pluck`, `group_by`, includes, transactions). Fields que continuam `String` também aceitam o enum: `eq`, `batch`, `.set(...)` (também em `Option<String>`) e `.into()` num literal da struct. Uma string gravada que não corresponde a nenhuma variante faz a leitura falhar em vez de adivinhar. Veja [Enums em colunas de string](/pt-br/docs/orm/guide/defaults-enums#enums-em-colunas-de-string).
- **`field.set_runtime_enum(...)` nos transforms.** No `dinoco/transform.rs`, `field.set_runtime_enum("crate::Permission")` troca um field `String` pelo enum, marca-o com `#[dinoco(enum)]` para que um field opcional não seja tomado por uma relação, e transforma um `@default("...")` de string na variante correspondente. Veja [Guardar um enum numa coluna de string](/pt-br/docs/orm/guide/transforms-recipes#guardar-um-enum-numa-coluna-de-string).
- Atualizando: nada muda para o código existente. `DinocoEnum` grava os mesmos valores de antes.

## v2.1.8

- **Agregações no `pluck`.** `find_many(...).pluck(|x| x.amount.sum())` faz o banco calcular `SUM`, `AVG`, `MIN`, `MAX` ou `COUNT` sobre as rows encontradas e retorna esse valor: `i64`/`f64` para uma soma (`0` sem nenhuma row), `Option<f64>` para uma média, `Option<T>` para um mínimo ou máximo, `i64` para uma contagem. `where_`, `where_complex` e filtros de relação escolhem as rows, e `take`/`skip` (com `order_by`) agregam uma janela delas, então `.order_by(|x| x.amount.desc()).take(10)` soma as dez maiores. As somas voltam convertidas para `i64`/`f64` no PostgreSQL (`numeric`) e no MySQL (`DECIMAL`). Veja [Agregue uma coluna](/pt-br/docs/orm/orm/find-many#agregue-uma-coluna).
- **Agrupe por um field, uma data ou um horário.** `.group_by(...)` depois de uma agregação retorna um `(chave, valor)` por grupo: `.group_by(|x| x.status)` pelos valores de um field (incluindo enums e fields opcionais), `.group_by(|x| x.created_at.date())` pela data completa (`day()` é o mesmo), `week()`, `month()`, `year()` pelo primeiro dia do período como `NaiveDate`, e `hour()`, `minute()` pelo instante em que a hora ou o minuto começa, como `DateTime<Utc>`. Os grupos vêm pela chave; `order_by` no field agrupado ordena pela chave, no field agregado pelo valor, e `take`/`skip` paginam os grupos. Agregações agrupadas ou não rodam dentro de transactions e aparecem nos hooks `on_find` como qualquer leitura. Veja [Agrupe a agregação](/pt-br/docs/orm/orm/find-many#agrupe-a-agregacao).
- **Ignore duplicados e receba a row existente.** `insert_into`/`insert_many` aceitam `.on_conflict_do_nothing(|x| x.email)` (uma tupla para um índice único com várias colunas): uma row que colide com uma existente é ignorada em vez de falhar com `CreateError::UniqueViolation`, e o resto do lote é inserido. Com `.returning::<S>()` ou `.pluck(...)`, cada payload recebe a sua row de volta, em ordem, a inserida ou a que já estava lá, o que transforma "busca ou cria" numa chamada só. Nenhum erro é gerado, então é seguro dentro de uma transaction no PostgreSQL. O MySQL não tem alvo de conflito e ignora um duplicado em qualquer índice único. Veja [Ignore duplicados e retorne a row existente](/pt-br/docs/orm/orm/insert#ignore-duplicados-e-retorne-a-row-existente).
- **Índices parciais.** `@unique`, `@index`, `@@uniques` e `@@indexes` aceitam uma condição entre `<` e `>`: `email String? @unique<email != null>`, `@@uniques<deleted_at == null && slug != "_">([tenant, slug])`. Um índice unique parcial só rejeita duplicatas entre as rows que batem, e um índice comum parcial só cobre essas rows. PostgreSQL e SQLite criam índices `... WHERE <condição>`; o MySQL, que não tem índices parciais, monta a chave de um unique com `CASE WHEN <condição> THEN coluna END` (8.0.13+) e cria um comum sobre todas as rows. As condições comparam fields com `null`, booleanos, números, strings e valores de enum, combinados com `&&`, `||`, `!` e parênteses; o compilador confere cada field e tipo de valor, o formatter as escreve na forma canônica, e a extensão do VS Code destaca, resolve e renomeia os fields dentro delas. Cada banco guarda a condição junto do índice, então a detecção de drift a compara e uma condição alterada recria o índice. Veja [Índices parciais](/pt-br/docs/orm/guide/indexes#indices-parciais).
- **`skip` sem `take` funciona no SQLite e no MySQL.** `find_many().skip(n)` escrevia `OFFSET` sem `LIMIT`, que os dois rejeitam como erro de sintaxe, então uma query que pulava rows sem limitá-las falhava ali (o PostgreSQL aceita). Agora o Dinoco escreve o valor "sem limite" de cada banco, `LIMIT -1` no SQLite e `LIMIT 18446744073709551615` no MySQL, no `find_many`, `.pluck(...)`, `.includes(...)`, agregações e agregações agrupadas. O PostgreSQL envia o mesmo SQL de antes. Veja [Paginação](/pt-br/docs/orm/orm/find-many#paginacao).
- **Um default de número inteiro num field `Float` não acusa mais drift.** `score Float @default(0)` fazia o `migrate generate` falhar logo depois de aplicar a migration no PostgreSQL e no MySQL, com `The migration finished, but the live database still does not match the Dinoco schema`: o schema tem o inteiro `0` e o banco reporta `0.0`. Agora um número inteiro bate como inteiro ou float, também contra os snapshots de schema gravados por versões anteriores. Veja [Defaults e enums](/pt-br/docs/orm/guide/defaults-enums).
- **Fields enum aceitam `pluck`.** `.pluck(|x| x.status)` funciona em fields de um tipo `DinocoEnum`, em todo builder que tem `pluck`.
- Atualizando: nenhuma migration é necessária. Código que monta um `InsertQuery` à mão acrescenta `on_conflict_do_nothing: None`. `DinocoSqlCompiler` ganhou dois methods (`compile_aggregate_query`, `compile_lookup_query`) e `MutationExecutor` um (`lookup`), que só implementações escritas à mão precisam. `find_many(...).pluck(...)` agora é genérico no que extrai (`P: IntoPluck<M>`), o que só importa para código que nomeia os parâmetros de tipo. `MigrationIndex` ganhou o campo `predicate` (`None` para um índice completo) e o `Attribute` do compilador o campo `condition`, para código que os monta à mão.
