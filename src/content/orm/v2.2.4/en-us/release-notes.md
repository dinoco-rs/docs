# Dinoco v2.2.4

This page tracks what changed release over release. Each entry links to the page that documents the feature in depth — treat this as a changelog, not the primary reference.

## v2.2.4

- **`empty()` and `not_empty()` on list relations.** One-to-many and many-to-many relation fields take two filters without a callback: `t.items.empty()` keeps the rows with no related row, and `t.items.not_empty()` the rows with at least one. They compile to the same `NOT EXISTS`/`EXISTS` subquery as `not_exists()`/`exists()`, which every relation keeps, and work wherever a relation filter does. Singular relations don't have them, so `t.payout.empty()` doesn't compile. See [Empty and non-empty lists](/en-us/docs/orm/orm/relation-filters#empty-and-non-empty-lists).
- **`find_many` counts next to its rows.** `.count()` returns the rows together with the model's count type, `(Vec<M>, M::Count)`, counted with the find's filters and without `order_by`, `take`, or `skip`: the page and the total a paginated list needs, in one call. `.count_transform(|count| ...)` starts from the find's filters and changes them for the count only, with the new `remove(|x| x.field)` on the count builder, and `.count_custom(...)`/`.count_custom_complex(...)` count with filters of their own; all three take `includes` for relation counts. The count runs first, and a page that starts past the last row runs no find. The future is a plain `find_many`'s plus the count type (416 bytes against 392 in the payments fixture), and it allocates no more than calling `find_many` and `count` one after the other. See [Count with the rows](/en-us/docs/orm/orm/find-many#count-with-the-rows).
- **`dinoco init` links to the documentation.** The link it prints at the end pointed to `https://dinoco.io/getting-started`, which doesn't exist. It now points to the [introduction](/en-us/docs/orm/guide/introduction).
- Upgrading: nothing changes for existing code. In a generated `Where`, a list relation's field is now a `RelationField<T, ListRelation>`, and `FindMany` and `FindManyTransform` take a last type parameter for the count (`NoCount` by default); only code that writes out those types in full needs the new parameter.

## v2.2.3

- **Seeds run on the runtime `#[tokio::main]` builds.** `dinoco seed` ran the seed on a single-threaded Tokio runtime, so application code it called that uses `tokio::task::block_in_place`, or blocks on a task it spawned, panicked or hung. It now runs on the multi-threaded runtime, as the runner before v2.2.2 did. See [How seeds run](/en-us/docs/orm/tooling/seeds#how-seeds-run).
- **`dinoco seed` builds only the package it runs in.** It selects the package in the current directory and only its library and binaries, so at the root of a workspace with `default-members` it no longer builds the other members, and a package with neither a library nor a binary gets an error instead of a run of its integration tests and doctests.
- Upgrading: nothing changes for existing code.

## v2.2.2

- **Seeds see the whole crate.** `dinoco seed` compiled the seed in a separate runner with only `dinoco/mod.rs`, so `use crate::{...}` found the models and nothing else: helpers, constants and anything the crate root imports failed with `unresolved import`. The seed now runs inside your application's crate, through a test that the generated `dinoco/mod.rs` declares, so `crate::...` resolves exactly as it does in the application, with its dependencies. See [How seeds run](/en-us/docs/orm/tooling/seeds#how-seeds-run).
- Upgrading: run `dinoco models generate` once so `dinoco/mod.rs` declares the seed's test; until then `dinoco seed` asks for it. The crate is compiled with `cfg(test)` to run the seed, so the generated `connect()` returns the test database there: use the `client` the seed receives.

## v2.2.1

> [!WARNING]
> Breaking change: every to-one navigation field is now `Option<Box<T>>`. Regenerate the models with `dinoco models generate` and follow the upgrade steps at the end of this section. The schema, the SQL and the database don't change.

- **Models never hold other models by value.** A many-to-one or one-to-one field generated as `Option<T>` (boxed only when relations formed a cycle), so a model held every model it pointed to, those held theirs, and the space was taken whether the include was loaded or not. In a payments schema where a support message points to its ticket and author, and those to charges, businesses and accounts, a `SupportMessage` took 13,992 bytes, a handler that kept one across an `.await` had a 22,592-byte future, a transaction that read one and wrote once had a 42,680-byte one, and reading a message with nested includes plus that transaction needed 1.1 MiB of stack in a debug build. Every to-one field is now `Option<Box<T>>`, 8 bytes loaded or not: the same message takes 160 bytes, the handler 584, the transaction 544, and the flow runs in 116 KiB of stack. Fields are read through the box as before, and serde reads and writes the same JSON. See [Navigation field types](/en-us/docs/orm/guide/relations#navigation-field-types).
- **Smaller futures in every builder.** `execute` keeps each part of the builder once instead of the builder and a copy of it, single-statement reads return the round trip's future instead of an `async fn` wrapped around it, `find_and_update` awaits relation updates boxed like `update` already did, and a transaction keeps the closure's result once while it commits. With the same schema, `find_first` and `find_many` (with or without includes) went from 1,112 to 392 bytes, aggregates from 1,400 to 360, `find_and_update` from 824 to 176, `update` from 280 to 104, `count` from 408 to 248 and `exists` from 208 to 72.
- **`Float @default(0)` compiles.** A whole-number default on a `Float` field generated `#[dinoco(default = 0)]` on an `f64`, which did not compile. It now generates `0.0`.
- Upgrading:
  - Run `dinoco models generate`. No migration is needed.
  - Reading a related model's fields compiles as before: `if let Some(account) = &session.account { account.email }`, `session.account.as_ref().map(|account| &account.email)`.
  - Code that needs the related model by value takes it out of the box with `*`: `let account: Account = *session.account.expect("account")`, or `session.account.map(|account| *account)` for an `Option<Account>`. A value built from several relations, such as `Option<(Account, Business)>`, becomes `Option<(Box<Account>, Box<Business>)>` unless you unbox each one. `session.account.as_deref()` gives an `Option<&Account>`.
  - Code that sets a to-one field boxes the model: `session.account = Some(Box::new(account))`.
  - Hand-written `#[derive(Entity)]` structs keep working with either `Option<T>` or `Option<Box<T>>`.
  - In `dinoco/transform.rs`, `Relation::ty` is `Box<T>` for every to-one relation; `relation.target` still names the model it points to.
  - The builders' `execute` methods return `impl Future` instead of being `async fn`, and so do the `dinoco_engine::Backend` methods that run one statement (`query`, `aggregate`, `lookup`, `insert`, `update`, `delete`, `count`, `exists` and the relation reads), which now compile their SQL when called rather than when first polled. `.execute(&client).await` doesn't change.

## v2.2.0

- **Order by several columns.** Each `order_by(...)` call now adds a column after the previous ones instead of replacing it, so `.order_by(|x| x.created_at.desc()).order_by(|x| x.id.asc())` compiles to `ORDER BY created_at DESC, id ASC`. It works in `find_many`, `find_first`, `pluck`, aggregates over a window of rows, and includes, where it also orders each parent's `take`/`skip` window. After `.group_by(...)`, a second `order_by` on the grouped field picks how ties on the aggregate break. See [Order results](/en-us/docs/orm/orm/find-many#order-results).
- **Group dates in a time zone.** `.with_timezone(&zone)` after `date()`, `day()`, `week()`, `month()`, or `year()` of a `DateTime` field computes the period in that zone instead of UTC, daylight saving time included: `.group_by(|order| order.created_at.date().with_timezone(&Sao_Paulo))`. Zones come from `chrono_tz`, now re-exported as `dinoco::chrono_tz`. PostgreSQL uses `AT TIME ZONE`, SQLite a function Dinoco registers on each connection, and MySQL `CONVERT_TZ`, which needs its time zone tables: without them the query fails with a hint instead of grouping under `NULL`. See [Group by date in a time zone](/en-us/docs/orm/orm/find-many#group-by-date-in-a-time-zone).
- **Includes: filters and pages at every level, documented.** Relation filters, `where_complex`, `order_by`, `take`, and `skip` apply at every level of nested includes and on every relation kind, and includes read inside transactions through `tx`; new tests cover all of it on SQLite, PostgreSQL, and MySQL. The includes page wrongly said reads with includes could not run inside a transaction. See [Order and page the relation](/en-us/docs/orm/orm/includes#order-and-page-the-relation).
- **Seeds.** `dinoco/seed.rs` (or `dinoco/seed/mod.rs`) holds the rows every environment needs, written with the generated models and builders in an `async fn seed(client: &DinocoClient)`, and `dinoco seed [--workspace name]` runs it against the workspace's database. The generated `dinoco/mod.rs` declares it as `pub mod seed`, so the editor checks it against the current models. See [Seeds](/en-us/docs/orm/tooling/seeds).
- **The runner reuses your build.** The program that applies `dinoco/transform.rs` (and now runs seeds) builds into your project's target directory with a copy of its `Cargo.lock`, so it no longer compiles Dinoco and the database drivers a second time: a first run that took about a minute and 1.2 GB now takes a few seconds once your application is built. See [Where the transform runs](/en-us/docs/orm/guide/transforms#where-the-transform-runs).
- Upgrading: code that called `order_by` twice expecting the second call to replace the first now orders by both; drop the first call. `dinoco_engine` users building queries by hand: `FindQuery::order_by` is an `OrderByList` (`FindOrderBy::Asc("id").into()`), `AggregateGroup` has a `then_by` field (`None` keeps the old order), and `GroupBy` has a `DateIn` variant.

## v2.1.9

- **Enums in string columns.** `#[derive(DinocoRuntimeEnum)]` turns a Rust enum into the values of a plain `String` column, such as permissions stored as `permission:view-users`: the column stays a string in the schema and the database, and no enum type or migration is involved. A model field holding the enum reads variants and writes strings in every builder (inserts, `update`, `update_many`, `find_and_update`, filters, relation filters, `pluck`, `group_by`, includes, transactions). Fields that stay `String` accept the enum too: `eq`, `batch`, `.set(...)` (also on `Option<String>`), and `.into()` in a struct literal. A stored string no variant maps to fails the read instead of guessing. See [Enums in string columns](/en-us/docs/orm/guide/defaults-enums#enums-in-string-columns).
- **`field.set_runtime_enum(...)` in transforms.** In `dinoco/transform.rs`, `field.set_runtime_enum("crate::Permission")` switches a `String` field to the enum, marks it `#[dinoco(enum)]` so an optional field is not taken for a relation, and turns a string `@default("...")` into the matching variant. See [Store an enum in a string column](/en-us/docs/orm/guide/transforms-recipes#store-an-enum-in-a-string-column).
- Upgrading: nothing changes for existing code. `DinocoEnum` writes the same values as before.

## v2.1.8

- **Aggregates in `pluck`.** `find_many(...).pluck(|x| x.amount.sum())` has the database compute `SUM`, `AVG`, `MIN`, `MAX`, or `COUNT` over the matching rows and returns that one value: `i64`/`f64` for a sum (`0` over no rows), `Option<f64>` for an average, `Option<T>` for a minimum or maximum, `i64` for a count. `where_`, `where_complex`, and relation filters pick the rows, and `take`/`skip` (with `order_by`) aggregate a window of them, so `.order_by(|x| x.amount.desc()).take(10)` sums the ten largest. Sums are cast back to `i64`/`f64` on PostgreSQL (`numeric`) and MySQL (`DECIMAL`). See [Aggregate a column](/en-us/docs/orm/orm/find-many#aggregate-a-column).
- **Group by a field, a date or a time.** `.group_by(...)` after an aggregate returns one `(key, value)` per group: `.group_by(|x| x.status)` by a field's values (enums and optional fields included), `.group_by(|x| x.created_at.date())` by full date (`day()` is the same), `week()`, `month()`, `year()` by the first day of the period as a `NaiveDate`, and `hour()`, `minute()` by the timestamp the hour or minute starts at, as a `DateTime<Utc>`. Groups come by key; `order_by` on the grouped field orders them by key, on the aggregated field by value, and `take`/`skip` page them. Grouped and single aggregates run inside transactions and report to `on_find` hooks like any read. See [Group the aggregate](/en-us/docs/orm/orm/find-many#group-the-aggregate).
- **Skip duplicates and get the existing row back.** `insert_into`/`insert_many` take `.on_conflict_do_nothing(|x| x.email)` (a tuple for a unique index over several columns): a row that collides with an existing one is skipped instead of failing with `CreateError::UniqueViolation`, and the rest of the batch is inserted. With `.returning::<S>()` or `.pluck(...)`, each payload gets its row back in order, the inserted one or the one already there, which turns "get or create" into one call. No error is raised, so it is safe inside a PostgreSQL transaction. MySQL has no conflict target and skips a duplicate on any unique index. See [Skip duplicates and return the existing row](/en-us/docs/orm/orm/insert#skip-duplicates-and-return-the-existing-row).
- **Partial indexes.** `@unique`, `@index`, `@@uniques`, and `@@indexes` take a condition between `<` and `>`: `email String? @unique<email != null>`, `@@uniques<deleted_at == null && slug != "_">([tenant, slug])`. A partial unique index only rejects duplicates among the rows that match, and a partial standard index only covers them. PostgreSQL and SQLite create `... WHERE <condition>` indexes; MySQL, which has no partial indexes, keys a unique one by `CASE WHEN <condition> THEN column END` (8.0.13+) and builds a standard one over every row. Conditions compare fields with `null`, booleans, numbers, strings, and enum values, combined with `&&`, `||`, `!`, and parentheses; the compiler checks every field and value type, the formatter writes them canonically, and the VS Code extension highlights, resolves, and renames the fields inside them. Each database keeps the condition next to the index, so drift detection compares it and a changed condition recreates the index. See [Partial indexes](/en-us/docs/orm/guide/indexes#partial-indexes).
- **`skip` without `take` works on SQLite and MySQL.** `find_many().skip(n)` wrote `OFFSET` with no `LIMIT`, which both reject as a syntax error, so a query that skipped rows without capping them failed there (PostgreSQL accepts it). Dinoco now writes each database's "no limit" value, `LIMIT -1` on SQLite and `LIMIT 18446744073709551615` on MySQL, in `find_many`, `.pluck(...)`, `.includes(...)`, aggregates and grouped aggregates. PostgreSQL sends the same SQL as before. See [Pagination](/en-us/docs/orm/orm/find-many#pagination).
- **A whole-number default on a `Float` field no longer reports drift.** `score Float @default(0)` made `migrate generate` fail right after applying the migration on PostgreSQL and MySQL, with `The migration finished, but the live database still does not match the Dinoco schema`: the schema has the integer `0` and the database reports `0.0`. A whole number now matches as an integer or a float, also against schema snapshots recorded by earlier versions. See [Defaults and enums](/en-us/docs/orm/guide/defaults-enums).
- **Enum fields can be plucked.** `.pluck(|x| x.status)` works on fields of a `DinocoEnum` type, in every builder that has `pluck`.
- Upgrading: no migration is needed. Code that builds an `InsertQuery` by hand adds `on_conflict_do_nothing: None`. `DinocoSqlCompiler` has two new methods (`compile_aggregate_query`, `compile_lookup_query`) and `MutationExecutor` one (`lookup`), which only hand-written implementations need. `find_many(...).pluck(...)` is now generic over what it plucks (`P: IntoPluck<M>`), which only matters to code that names its type parameters. `MigrationIndex` has a new `predicate` field (`None` for a full index) and the compiler's `Attribute` a new `condition`, for code that builds them by hand.
